# Release v2026.10.28.1

- Previous production release: [v2026.10.26.1](v2026.10.26.1.md) (`5526a42a`, server and runner)
- Tag `v2026.10.27.1` was created but never deployed: the Codex state
  classification refused an app-server home entry
  ([issue #859](https://github.com/sakuraiyuta/kaoiro/issues/859)). This
  release carries everything it would have and the fix.
- Range: `v2026.10.26.1..v2026.10.28.1`; the code range
  `v2026.10.26.1..388146eb` has 65 commits, including the two that added the
  earlier note for `v2026.10.27.1`, and not counting this note
- Release class: high risk
  ([High-risk change release](../operations/high-risk-change-release.md)),
  so it goes through the operator's release card with the canary stage. The
  Codex CLI, SDK and native binary pins change from 0.161.0 to 0.164.0, which
  no path rule catches and the page says to treat as high risk for the
  affected engine. `wrapper/agent-common/src/inter_agent.ts` is a listed TL
  candidate path and changes here (work stamp rendering, follow-up guidance),
  so unless a reviewer judges otherwise in writing, the canary covers every
  engine, not only Codex. `runner/deploy/**` is a listed FS candidate path and
  now changes in executable code (Codex state classification and admission,
  [issue #859](https://github.com/sakuraiyuta/kaoiro/issues/859)); the release
  is already high risk, so the card and canary apply, and no separate written
  FS judgement was made for that change. U1 of [issue #564](https://github.com/sakuraiyuta/kaoiro/issues/564) on its own was
  judged neither FS nor TL
  ([issue #564](https://github.com/sakuraiyuta/kaoiro/issues/564#issuecomment-6446972729)).
  The server change touches the delivery ledger record and the join snapshot,
  so the server and the runner are updated to the same commit.

## Highlights

- **Codex CLI and SDK 0.164.0** (from 0.161.0), with **GPT-6.1 Terra** in the
  curated catalog
  ([issue #810](https://github.com/sakuraiyuta/kaoiro/issues/810),
  [issue #809](https://github.com/sakuraiyuta/kaoiro/issues/809)). The home
  classification used by Codex state backup was re-derived for 0.164.0
  ([issue #817](https://github.com/sakuraiyuta/kaoiro/issues/817)).
- **Codex state classification recognizes external daemon home entries.**
  An interactive Codex TUI can start a shared daemon that leaves entries in
  the Codex home; the classification, transaction admission and stopped
  snapshot/restore now classify four such roots and refuse, with named codes,
  while an external writer or runtime marker remains
  ([issue #859](https://github.com/sakuraiyuta/kaoiro/issues/859)).
- **Preparation tool for the later Codex backend default change**
  (`scripts/codex-backend-compatibility.mjs`, U1 of
  [issue #564](https://github.com/sakuraiyuta/kaoiro/issues/564)). The default
  backend does not change in this release.
- **A pending permission or question survives later envelopes.** A dashboard
  reload no longer hides the dialog an agent is still blocked on
  ([issue #503](https://github.com/sakuraiyuta/kaoiro/issues/503)).
- **The delivery binding survives a ledger restart.** Channels that were
  already joined keep acknowledging and reporting without rejoining
  ([issue #512](https://github.com/sakuraiyuta/kaoiro/issues/512)).
- **An assignee sees the `work_id`** of an assignment in the delivered
  message ([issue #690](https://github.com/sakuraiyuta/kaoiro/issues/690)).

## Changes

### Codex

- `@openai/codex` and `@openai/codex-sdk` are pinned to 0.164.0. The
  LF-only stream-reader patch is re-keyed to the new SDK with unchanged
  contents. A fresh approval/decline fixture was captured from the 0.164.0
  native and the older fixtures are kept. Native checks use isolated homes and
  a loopback provider on both backends; signed-in server defaults remain
  unverified
  ([issue #810](https://github.com/sakuraiyuta/kaoiro/issues/810), [evidence](../evidence/codex-app-server/pin-0.164.0-adoption-gates-2026-10-27.md)).
- The curated catalog gains `gpt-6.1-terra` (efforts low to ultra, default
  low), offered after Astra. It is shared by paid ChatGPT plans and API-key
  authentication; Free/Go keep advertising `gpt-5.6-terra` only. The upstream
  entry declares no minimum client version; the catalog uses 0.161.0, the
  lowest version on which a real turn was observed
  ([issue #809](https://github.com/sakuraiyuta/kaoiro/issues/809),
  [Codex model catalog](../reference/engines/codex-model-catalog.md)).
- Codex state backup: the runbook and the snapshot classifier comment now cite
  0.164.0. An isolated measurement found the same 28 home-root names on 0.161.0
  and 0.164.0 with both backends, and the classifier of that time accepted all
  of them. That measurement used the stdio path and did not exercise the Unix
  listener of an interactive client; see the Runner section below. A configured `log_dir` can move the
  logs database and its lock; the runbook says not to place it inside a
  disposable subtree. The cloud-config cache condition now also names the
  Sci/SciPlus plans
  ([issue #817](https://github.com/sakuraiyuta/kaoiro/issues/817),
  [issue #822](https://github.com/sakuraiyuta/kaoiro/issues/822)).

### Server

- `AgentStates` keeps the stored `pending_permission` and `pending_question`
  when a later envelope that does not speak about pending state (for example
  `instruction_rejected` or `attach_rejected`) becomes the latest one. The join
  snapshot and the broadcast both carry it; a disconnect still drops it
  ([issue #503](https://github.com/sakuraiyuta/kaoiro/issues/503)).
- A skip-v1 delivery bind now mints a binding token that is persisted with the
  recipient entry and presented by the channel on acknowledgements, resync,
  stage reports, yield claims and terminate-time retirement. A ledger restart
  keeps the entry and the token, so the bound channel continues; a superseded
  channel of the same generation is still rejected. A row without a token
  (written before this release, or by an older server) is rejected until the
  wrapper rejoins
  ([issue #512](https://github.com/sakuraiyuta/kaoiro/issues/512),
  [Delivery](../reference/inter-agent/delivery.md)).
- The delivery-loss dispatcher skips a tick when a store it reads is between a
  stop and its restart, instead of terminating. A store that stops while a call
  is in flight, or any other failure, still terminates it and the supervisor
  restarts it
  ([issue #505](https://github.com/sakuraiyuta/kaoiro/issues/505),
  [issue #570](https://github.com/sakuraiyuta/kaoiro/issues/570)).
- Wrapper ingress for `session_lifecycle` logs and drops every server-only kind
  (`disconnected`, `reconnecting`, `reconnected`, `session_reset_started`,
  `session_reset_completed`, `permission_requested`), so a wrapper cannot write
  an event the timeline would read as recorded by the server. No known wrapper
  emits these kinds
  ([issue #683](https://github.com/sakuraiyuta/kaoiro/issues/683)).
- Read-only, host-scoped observation of directory, pointer, state, connection,
  reset and pending-transition membership, used by the preparation tool. It
  excludes session IDs, working directories, snapshots and envelope contents
  ([issue #564](https://github.com/sakuraiyuta/kaoiro/issues/564)).

### Wrappers

- The inbound message rendered to the model now carries the server's `work`
  stamp (`work_id`, state, revision, authority epoch). An assignment in state
  `nominated` also gets a line telling the assignee to call `accept_assignment`
  or `decline`. Malformed stamps render nothing
  ([issue #690](https://github.com/sakuraiyuta/kaoiro/issues/690),
  [Send and wait](../reference/inter-agent/send-and-wait.md)).
- A send whose own `done: true` closes the conversation no longer reports a
  missing follow-up authorization, and the `delivery_lost` guidance no longer
  claims it always resolves the waiter. The `operation_id` description tells
  callers to omit it
  ([issue #686](https://github.com/sakuraiyuta/kaoiro/issues/686)).

### Runner

- Codex state classification, transaction admission and the stopped
  snapshot/restore boundaries recognize four exact home-root names. The Unix
  listener control tree `app-server-control` is disposable: forward backup
  omits it from the manifest and payload and leaves the source untouched, and a
  full restore leaves it in quarantine. `app-server-daemon`, `packages` and
  `tui-thread-reference-capabilities` are state and are preserved byte for
  byte. Similar or unknown root names get no exemption
  ([issue #859](https://github.com/sakuraiyuta/kaoiro/issues/859),
  [daemon home evidence](../evidence/codex-app-server/daemon-home-2026-10-28.md)).
- An external Codex daemon is not state to be copied: classification,
  admission and the stopped boundaries (including a quarantined original home
  on resume) refuse with exit 78 and one of three codes while a control alias,
  PID/startup/socket marker or installer directory lock exists
  (`CODEX_EXTERNAL_DAEMON_ENTRY`), while a startup, daemon-operation, PID
  reservation or installer file lock is held
  (`CODEX_EXTERNAL_DAEMON_BUSY`), or when ownership, type or lock inspection
  cannot be established (`CODEX_EXTERNAL_DAEMON_CHECK_FAILED`). An unknown
  result never counts as unheld, and no refusal removes anything
  ([runbook](../operations/runner-update-and-rollback.md#external-codex-daemons-and-their-home-entries)).
- Lock inspection needs `/usr/bin/flock` on the Linux maintenance path. It
  opens existing regular files read-only without following symlinks and closes
  every descriptor. A live classification briefly takes an available lock, so
  do not classify repeatedly a home with active external clients.

### Operations

- `scripts/codex-backend-compatibility.mjs --phase prepare` prepares an
  affected host for a later default change. It reads the host union from the
  server, verifies the runner identity from the public startup record
  (`runner: host=<host_id> rev=<sha> connecting to ...`) and the applied backend
  selection, and only then writes `codex.backend: "exec"`. Before the write,
  unavailable or changed observations, a missing, ambiguous or oversized
  startup record (`runner-start-record-unavailable`), or a dirty revision
  (`runner-identity-dirty`) stop preparation without changing the
  configuration. If acknowledgement or post-write verification fails, the
  explicit `exec` write may already remain; the command stops without an
  additional write, rollback or restore. It never restarts the service and
  never switches an explicit backend. The runner's `--version --json` reports its full
  `revision` and a boolean `dirty`
  ([Backend switching runbook](../operations/codex-backend-switch.md#preparation-before-a-default-change),
  [evidence](../evidence/codex-app-server/issue-564-u1-compatibility-2026-10-27.md)).

## Operator steps

- **Update the server and the runner to the same commit, through the release
  card** ([High-risk change release](../operations/high-risk-change-release.md)).
  Fill the card before switching anything. The pin change makes B2 apply: record
  the rollback targets and the verified physical path of the tool release and
  the snapshot directory. Run the canary stage for each affected engine in
  turn; a failed or timed-out canary turn means roll back at once.
- **Update Codex to 0.164.0.** The runner carries the pinned CLI, SDK and native
  binary, so the release itself moves them. Because the native pin changes,
  follow [Codex state backup](../operations/runner-update-and-rollback.md#codex-state-backup):
  before stopping the runner, run the candidate release's metadata-only
  classification against the production home. A refusal aborts the update
  before the runner is stopped; do not delete or rename files to make it pass.
  Do not set `log_dir` or `sqlite_home` inside a disposable Codex home subtree.
  If an interactive `codex` (the TUI, or its shared daemon) was ever started
  against the target Codex home, stop its external writers first, as below.
  Hosts that authenticate with a Sci/SciPlus workspace need the separate
  cache-classification review described in the runbook.
- **Stop external Codex daemons before the update.** On a host where an
  interactive `codex` was started against the target Codex home, the update's
  classification refuses while its daemon, updater or installer entries remain.
  With operator authorization, follow the runbook's
  [external daemon procedure](../operations/runner-update-and-rollback.md#external-codex-daemons-and-their-home-entries):
  close same-home clients and disable their restart; stop the independent
  updater first, using only a verified PID; run `app-server daemon stop` with
  the matching CLI against that home; confirm there are no live external
  writers. A residual stale PID or socket entry needs a separate approval to
  unlink that exact entry; stopping the daemon is not approval to delete files,
  and a lock is never removed. Keep interactive use on a separate home where
  possible, and do not restart external clients until validation ends.
- **If a classification is refused, follow the runbook's table.**
  `CODEX_EXTERNAL_DAEMON_ENTRY`: identify and stop the intended writers and
  obtain approval for any exact stale-entry disposition.
  `CODEX_EXTERNAL_DAEMON_BUSY`: wait for the identified operation to stop and
  never unlink the lock. `CODEX_EXTERNAL_DAEMON_CHECK_FAILED`: resolve the
  inspection failure and rerun; an unknown result never means unheld. Any
  other refusal still aborts the update before the runner is stopped.
- **The preparation tool is installed by this release but the default does not
  change.** Omitting `codex.backend` still selects `exec`. The default
  changes in a later release (U2 of
  [issue #564](https://github.com/sakuraiyuta/kaoiro/issues/564)), and only hosts that omit the
  setting need `scripts/codex-backend-compatibility.mjs --phase prepare`
  before that release. Running it now is optional; follow the runbook's
  procedure and its stop conditions, and expect the runner revision it checks
  to be clean. A host with an observed, applied explicit `codex.backend`
  setting that it will retain (explicit `exec` or explicit `app-server`) needs
  no preparation, regardless of how its sessions were created. Do not overwrite
  an explicit `app-server` setting with `exec` to prepare.
- **Advance notice for API-key authentication.** The app-server default planned
  for the later release has not been measured with API-key authentication
  (model and effort defaults, credential lifecycle). API-key mode stays a
  supported option; this is an unmeasured limit, not a passed measurement. If
  you use API-key authentication and need the current `exec` behavior to
  continue after that release, set `codex.backend` to `exec` explicitly. If the
  host already has app-server sessions, first follow the runbook's guarded
  fresh-backend transition; selecting `exec` does not authorize resuming
  existing app-server IDs through `exec`.
- Rolling back to v2026.10.26.1 also moves the Codex pin back to 0.161.0, so
  treat it as a native pin change under the same card and state backup rules.
  Use the recorded physical tool release that recognizes all four daemon
  home roots for the state-aware steps, including when selecting older
  application or native code; older helpers refuse these names.
  The old server can read delivery-ledger rows written by this release. Its
  writes omit the binding token. When returning to this release, wrappers must
  rejoin to mint a new binding; no manual DETS conversion is required.
