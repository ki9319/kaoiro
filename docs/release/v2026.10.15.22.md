# Release v2026.10.15.22

- Deployed: 2026-10-16 (server and runner)
- Commit: `fed60d78c1031dc48b72f1d1e780c829911d9080`
- Previous production release: [v2026.10.15.17](v2026.10.15.17.md) (`f3d8a8fe`, server and runner)
- Range: `v2026.10.15.17..v2026.10.15.22`, 6 commits
- Release class: TL (the shared core transport and all four engine CLIs), plus a server update

## Highlights

- A Grok Build peer resumed from a `danger-full-access` history runs operator
  instructions and inter-agent messages again ([issue #671](https://github.com/sakuraiyuta/kaoiro/issues/671)).
- `whoami` reports the agent's current display name on every engine
  ([issue #672](https://github.com/sakuraiyuta/kaoiro/issues/672)).

## Changes

### All engines

- The shared core accepts a permission observation without `enforcement` and
  keeps the field omitted ([issue #671](https://github.com/sakuraiyuta/kaoiro/issues/671)).
  Before, it dropped the whole `permission_sync` that echoed such an
  observation, so a Grok Build peer with the sandbox off waited for the sync
  forever after a resume. A present but invalid value is still rejected, and
  constraints still require `enforcement`.
- `whoami` returns `display_name`, read from the server's peer directory when
  the tool is called, next to the unchanged canonical `persona`
  ([issue #672](https://github.com/sakuraiyuta/kaoiro/issues/672)). When the
  name cannot be confirmed, the field is omitted rather than filled from an
  older local name or `persona.name`.

### Server

- `directory_request` accepts `scope: "self"`, which returns only the calling
  agent's own entry, with the same display-name rules as `list_agents`
  ([issue #672](https://github.com/sakuraiyuta/kaoiro/issues/672)). Other
  scope values are rejected.

## Upgrading

- No configuration change.
- Update the server and the runner to the same commit.
- The release is TL: follow the canary stage in
  [High-risk change release](../operations/high-risk-change-release.md).
  Only a Grok Build peer whose history was recorded under `danger-full-access`
  exercises the fix for issue #671; resume one such peer in the canary.

## Known issues

- A Claude Code peer still cannot send `send_to_agent` from a turn started by a
  `run_in_background` Bash or a Monitor notification
  ([issue #674](https://github.com/sakuraiyuta/kaoiro/issues/674)), or after a
  background Agent hand-back ([issue #426](https://github.com/sakuraiyuta/kaoiro/issues/426)).
- The permission-sync wait has no timeout
  ([issue #673](https://github.com/sakuraiyuta/kaoiro/issues/673)).
