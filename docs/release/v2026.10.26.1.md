# Release v2026.10.26.1

- Previous production release: [v2026.10.25.1](v2026.10.25.1.md) (`72ba36fd`, server and runner)
- Range: `v2026.10.25.1..v2026.10.26.1`
- Release class: neither FS nor TL
  ([High-risk change release](../operations/high-risk-change-release.md)).
  The only TL candidate path, `wrapper/core/src/transport.ts`, gains a
  parser for one rejection reason that never throws and is not on the turn
  path. No SDK, CLI or native pin changed. The server change touches
  persisted settings, operator-only channel events, environment variables and
  delivery replies, so the release goes through the operator's release card
  rather than the ordinary release path.

## Highlights

- **Configurable work-item admission limits.** The per-principal nominated
  limit and the per-assignee active limit (0 means no limit) are read from
  the server environment and can be changed by the operator in the dashboard.
  The setting is persisted; a refused work operation reports the effective
  capacity
  ([issue #786](https://github.com/sakuraiyuta/kaoiro/issues/786)).
- **Bandit 1.14.0** clears eleven advisories in Bandit 1.13.1. HTTP/2 stays
  disabled
  ([issue #803](https://github.com/sakuraiyuta/kaoiro/issues/803)).

## Changes

### Server

- `KAOIRO_WORK_NOMINATED_PER_PRINCIPAL` and `KAOIRO_WORK_ACTIVE_PER_ASSIGNEE`
  set the admission limits; an invalid value stops the server at startup.
  Operator-only `get_work_settings` and `set_work_settings` on
  `agents:lobby`, with role-filtered `work_settings` broadcasts. The saved
  setting is a new record in the work store; if it is invalid or unreadable,
  work mutations are refused until it is repaired
  ([Server configuration](../reference/configuration/server.md),
  [issue #786](https://github.com/sakuraiyuta/kaoiro/issues/786)).
- A work operation refused for capacity replies with reason `work_capacity`
  and the effective limits
  ([issue #786](https://github.com/sakuraiyuta/kaoiro/issues/786)).
- Bandit 1.14.0. Standards-conforming clients and proxies are unaffected.
  Non-conforming HTTP/1 requests and WebSocket handshakes now get 400, and a
  WebSocket closed by the server is closed within the close timeout
  ([issue #803](https://github.com/sakuraiyuta/kaoiro/issues/803)).

### Dashboard

- Settings drawer: operator controls for the work admission limits
  ([issue #786](https://github.com/sakuraiyuta/kaoiro/issues/786)).

### Wrappers

- The capacity details of a `work_capacity` rejection are passed to the
  agent; malformed or unknown details are ignored
  ([issue #786](https://github.com/sakuraiyuta/kaoiro/issues/786)).

### Development

- Test pins left after the issue 709 P3 retirement
  ([issue #757](https://github.com/sakuraiyuta/kaoiro/issues/757)).

## Operator steps

- If you set `KAOIRO_WORK_NOMINATED_PER_PRINCIPAL` or
  `KAOIRO_WORK_ACTIVE_PER_ASSIGNEE`, each must be an integer from 0 to
  2147483647, or the server does not start. Unset values use the default.
- Rolling back to v2026.10.25.1 keeps the server starting: the previous
  release ignores the new settings record, so limits changed in the dashboard
  stop applying until the server is updated again.
